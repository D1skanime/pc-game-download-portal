# Plan: Deduplicate duplicate PC DLC provider media imports

## Objective

Prevent automatic PC DLC provider media imports, especially IGDB screenshots, from creating multiple database rows for the same image content. Replace the current provider/candidate/position identity with a stable content-based identity while reusing the existing PC component media, storage, placement, and cleanup flows.

Handle legacy duplicate rows conservatively: merge only rows in the same DLC component, provider, and media role when their stored bytes have an exact matching SHA-256. Preserve placements and remove only files proven to be unreferenced after the database reconciliation. Do not perform broad deletion or change user-upload semantics.

## Current findings

- The automatic path is `backend/endpoints/sockets/scan.py::_enrich_pc_dlc_from_igdb`.
- It currently hashes `candidate.provider:candidate.id:position:role`, so the same bytes at a different candidate position receive a different `provider_media_id`.
- `FSResourcesHandler.store_pc_component_provider_image` already owns HTTPS validation, image validation, size limits, MIME detection, and writing below the RomM-owned resource root. It is also used by manual PC metadata selection in `backend/endpoints/roms/pc_metadata.py`.
- `DBRomHandler.import_pc_component_provider_media` inserts screenshot rows without a complete inventory reconciliation. Its existing non-screenshot replacement behavior must remain compatible.
- `RomComponentOwnedMediaPlacement` is component-scoped and cascades on media deletion. A duplicate merge must preserve a placed row, transfer placement when only the duplicate was placed, and compact positions through the existing placement semantics.
- PC component-owned media has no content digest today. Existing rows therefore cannot be safely classified as duplicates from database fields alone.
- File cleanup is already returned from database mutations as paths and performed through `fs_resource_handler.remove_file` after the transaction. The fix must continue that ordering and tolerate an already-missing duplicate file as the existing delete path does.
- Manual metadata selection uses candidate media IDs for the review API. Those review IDs must remain unchanged, while the persisted provider identity should use the shared content-based identity after the image is stored.

## Implementation tasks

### 1. Add a shared content identity to the existing provider-image storage flow

Files:

- `backend/handler/filesystem/resources_handler.py`
- A small existing media utility or provider-media helper, only if needed for the shared identity function
- `backend/endpoints/sockets/scan.py`
- `backend/endpoints/roms/pc_metadata.py`

Plan:

- Extend the existing provider-image storage result to expose the validated content SHA-256 along with the owned path and MIME type. Do not download the image a second time or create a parallel storage path.
- Keep the current HTTPS, content-type, 10 MiB, PIL validation, and RomM-owned storage-root checks unchanged.
- Derive a versioned stable `provider_media_id` from provider, role, and the validated content digest. The ID must be independent of candidate ID, source URL, and array position, and remain within the existing provider-ID length limit.
- Use one shared helper from both automatic IGDB enrichment and manual PC metadata selection. Preserve candidate media IDs only as review/selection identifiers.
- Keep filenames deterministic from the component, role, and content identity so repeated imports reuse the same logical path and do not create position-based files.

### 2. Persist content evidence and add scoped reconciliation

Files:

- `backend/models/rom.py`
- New Alembic revision after the current head, for example `backend/alembic/versions/0137_pc_component_provider_media_content_identity.py`
- `backend/handler/database/roms_handler.py`

Plan:

- Add a nullable SHA-256 content column for `RomComponentOwnedMedia`, with a component/provider/role/content lookup index. Keep it nullable for legacy rows that cannot be proven from database data alone. Do not expose it in the public response schema unless the existing API contract requires it.
- Update the provider import mutation to be idempotent for the stable identity. Reuse the existing component/version guard and return the existing row when the same provider, role, and content identity is imported again.
- Preserve current role behavior, especially the existing replacement semantics for non-screenshot provider roles, while ensuring an exact content duplicate is never appended as a second row.
- Add a narrowly scoped reconciliation helper for legacy rows. It may receive content hashes computed by the storage layer for provider-origin rows in the current DLC component, then:
  - group only by the current component, provider, role, and exact content SHA-256;
  - choose a canonical row deterministically, preferring an already placed row, then the lowest placement position, then oldest creation time/lowest ID;
  - retain the canonical row and stable identity;
  - move a placement from a duplicate to the canonical row only when the canonical row has no placement, otherwise preserve the canonical placement and compact positions;
  - return duplicate owned paths only after confirming they are no longer referenced by a surviving row;
  - leave uploads, other components, other providers, different roles, missing files, unreadable files, and differing hashes untouched.
- Keep stale expected-version, component scoping, authorization boundaries, and delete/placement cascade behavior unchanged.
- Do not remove provider rows merely because a provider response no longer includes them. This task prevents duplicate creation and merges proven duplicates without changing operator deletion semantics.

### 3. Reconcile legacy duplicates through existing storage access

Files:

- `backend/handler/filesystem/resources_handler.py`
- `backend/handler/database/roms_handler.py`
- `backend/endpoints/sockets/scan.py`

Plan:

- During the existing enrichment of the DLC currently being scanned, inspect only its provider-origin component media rows and compute hashes through the existing RomM-owned storage access. Do not use raw paths from request input or scan candidates.
- Backfill the nullable content digest only for readable, valid existing provider files in that component.
- Invoke the database reconciliation in the same component/version-controlled mutation flow before or as part of importing the current candidate media.
- After the database transaction commits, remove only the returned duplicate paths through `remove_file`. Treat `FileNotFoundError` as already-cleaned state, and do not use directory globs or parent-wide cleanup.
- If a legacy file cannot be read or validated, preserve its row and path so the operator can remove it explicitly. The importer must not guess that an unreadable row is a duplicate.

### 4. Update tests for identity, duplicate repair, placement, and cleanup

Files:

- `backend/tests/handler/filesystem/test_resources_handler.py`
- `backend/tests/handler/database/test_pc_component_resources.py`
- `backend/tests/handler/database/test_pc_igdb_enrichment.py`
- `backend/tests/endpoints/sockets/test_scan.py`
- `backend/tests/endpoints/roms/test_pc_metadata.py`
- Add a focused migration/model test only if the repository's existing migration coverage requires it.

Test cases:

- The storage helper returns a deterministic digest for identical bytes and retains existing validation and MIME behavior.
- Two IGDB candidate media entries with different positions and URLs but identical bytes produce one stable provider identity and one persisted component row.
- Repeated scans with the same content are idempotent and do not increase the screenshot row count.
- Different bytes, different roles, different providers, and sibling DLC components remain distinct.
- A legacy duplicate pair with identical readable bytes is merged only inside the current component/provider/role scope.
- Placement is preserved or transferred deterministically, positions remain unique and compact, and unplaced duplicates do not create an overview image.
- Upload-origin media and legacy rows with missing/unreadable files are not merged or deleted.
- Duplicate file cleanup happens after the database mutation, removes only unreferenced paths, and tolerates an already-missing path.
- Manual metadata selection keeps its candidate media IDs and still stores selected media through the same stable content identity.
- Existing stale-version, unknown-component, delete, and placement tests continue to pass.

## Acceptance criteria

1. The same provider image content imported at different candidate positions resolves to one stable provider media identity.
2. Repeating the scan does not create additional rows or files for unchanged content.
3. Existing exact duplicates are merged only when content equality is proven and scope is the same.
4. Placement order and overview selection remain valid after a merge.
5. Duplicate file cleanup is transaction-safe, path-scoped, and tolerant of already-missing files.
6. Uploads, different providers, roles, DLC components, and unreadable legacy rows are not broadly deleted.
7. Automatic scans and manual PC metadata selection share the same storage and identity helper.
8. Focused tests, migration checks, and relevant lint/type checks pass.
9. No deployment is performed as part of this planning task.

## Out of scope

- No broad cleanup of all RomM media or all IGDB rows.
- No deletion based only on URL, filename, candidate position, or a missing file.
- No change to parent-game media, non-PC platforms, user-upload behavior, authorization, or frontend layout.
- No deployment, source implementation, or commit in this planning-only task.
