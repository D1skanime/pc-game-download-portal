<interfaces>
From 14-01 and 14-02: each `DownloadManifest` persists the canonical selected game as `rom_id` with a relationship to `Rom`; it is not reconstructed from selected component rows. `db_download_manifest_handler.create_manifest(user_id, rom_id, component_ids)` creates only complete aggregates. `get_manifest(manifest_id, user_id)` performs an owner-scoped aggregate lookup, eagerly resolves and returns that aggregate's canonical `manifest.rom` relation with the aggregate, then evaluates lifecycle state. A missing or foreign-owner aggregate has the same bounded not-found outcome. Its closed lifecycle error outcomes are the source for bounded HTTP results.

HTTP contract to create: `POST /api/roms/{rom_id}/download-manifests` with `component_ids: null` for whole game or a non-empty unique positive list for exact components. HTTP contract to retrieve: `GET /api/download-manifests/{manifest_id}`. POST loads its path ROM; because GET has no ROM identifier, it must first obtain the owner-scoped aggregate and its persisted canonical `manifest.rom`, then call `assert_rom_visible(request, manifest.rom)` before serializing any GET output. Both require `Scope.ROMS_READ` and visibility masking.
</interfaces>
