# Phase 6 - UI Design Contract

> Visual and interaction contract for the frontend-adjacent Phase 6 gap closure. Generated by gsd-ui-researcher for gsd-ui-checker, gsd-planner, and gsd-executor.

---

## Contract Scope

This contract is intentionally bounded. It does not reopen completed Phase 6 decisions and does not design the Phase 7 storage administration experience.

The only runtime UI change in scope is safe replacement of the primary manual in the active v2 Game Details manual subtab. A primary manual is a RomM-owned resource stored through the typed `RESOURCES` descriptor. Shared or source-tree manuals remain immutable and must not regain upload, rename, move, overwrite, or delete controls.

The active-v2 semantic mutation inventory is also in scope, but only as a build-time test and guardrail. It has no runtime screen, notification, setting, or user copy.

## Layout and Component Contract

The current PDF or Markdown manual viewer is the primary visual anchor. Upload manual or Replace manual is the secondary action focal point. Ownership help, progress, and notifications support those two levels and must not become competing panels or primary headings.

### Existing manual

Keep the current ManualSubtab composition and dimensions:

1. The current PDF or Markdown viewer remains mounted and readable during replacement.
2. The overlay `RDropzone` continues to wrap the viewer, but accepts exactly one PDF or Markdown file and is disabled while a primary-manual mutation is pending.
3. The full-width footer `RBtn` label is `Replace manual`, uses the existing small outlined treatment, shows its built-in loading state after the standard 200ms debounce, and receives `aria-busy="true"` while pending.
4. A concise ownership helper is associated with the replace control: `Primary manuals are stored in RomM resources. Replacing one does not change files in your game library.`
5. Download, Re-download, and Delete icon-only controls retain localized accessible names through their existing `aria-label` or primitive tooltip contract in idle, pending, and disabled states.
6. Delete and re-download controls remain visible according to existing permission rules, but are disabled while upload or refresh is pending so manual mutations cannot race.
7. No dialog opens for replacement. `ManualUploadTargetDialog` may remain as a nonvisual coordinator only if it exposes the per-ROM pending result to ManualSubtab. It must not introduce a target-choice surface or source-folder option.

### Empty manual

1. Keep the existing editable `RDropzone` CTA and read-only `REmptyState`.
2. The file picker is single-select, with `accept="application/pdf,.md"`.
3. The heading remains `No manual yet`.
4. Editable users see the Upload manual CTA and the ownership/format body copy from the copywriting contract.
5. Users without `rom.edit` see the heading and explanatory body, with no upload affordance.
6. The optional Re-download action remains available only when the current API-backed source supports it and no manual mutation is pending.

### Selection and request boundary

1. A user gesture produces at most one `File`. Remove multi-file semantics from the primary-manual API call and UI.
2. The shared service accepts a singular file argument and sends exactly one POST. It must not map files into promises or use `Promise.allSettled`.
3. The client maintains at most one primary-manual request per ROM. A second local gesture while pending is ignored because every entry point is disabled. The server remains authoritative and rejects cross-tab or cross-client concurrency.
4. Never queue several selected files. Never silently replace one primary manual repeatedly in selection order.
5. The upload tracker contains one request record for this operation. Retry of the same filename must not update a stale failed record; clear or uniquely identify the prior request record before retry.
6. The visible feature owns pending state. A fire-and-forget emitter handler that leaves ManualSubtab interactive does not satisfy this contract.

## Interaction and State Contract

| State                             | Visible contract                                                                                       | Enabled actions                                                                           | Data contract                                                                       | Announcement                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Empty idle                        | Empty dropzone and Upload manual CTA                                                                   | Pick/drop one file; optional re-download                                                  | No primary manual                                                                   | None                                                                     |
| Existing idle                     | Current viewer, ownership helper, Replace manual button                                                | View, replace, delete, re-download according to permission                                | Current `path_manual` is authoritative                                              | None                                                                     |
| Native picker open                | Browser/OS picker only                                                                                 | Select one PDF or Markdown file or cancel                                                 | No request before selection                                                         | Native behavior                                                          |
| Upload pending                    | Prior viewer or empty state remains in place; replace/upload button loads; one UploadProgressToast row | Viewing and scrolling remain available; upload, drop, delete, and re-download are blocked | Current manual and `path_manual` remain unchanged until server success              | Localized polite live status: Uploading manual... or Replacing manual... |
| API success, refresh pending      | Same stable layout; mutation controls remain blocked                                                   | View/scroll only                                                                          | New manual is committed; client refreshes the same ROM before announcing completion | No premature success                                                     |
| Success                           | Refreshed viewer selects the primary manual and uses the updated cache-bust value                      | Normal actions restored                                                                   | New `path_manual` replaces the prior owned resource                                 | Manual uploaded successfully. or Manual replaced successfully.           |
| Upload failure                    | Prior viewer remains byte-for-byte and visually unchanged, or empty state remains empty                | Retry is available                                                                        | No path or prior-file loss                                                          | Safe upload/replace failure copy                                         |
| Concurrent request rejected       | Prior state remains; no optimistic viewer change                                                       | Retry only after the other request completes                                              | Server conflict is authoritative                                                    | Another manual upload is already in progress...                          |
| Refresh failure after API success | Keep the currently rendered snapshot; restore actions only after pending request ends                  | Reload is the recovery                                                                    | Do not claim that the prior manual is still authoritative                           | Manual saved, but this page couldn't refresh. Reload to view it.         |
| Invalid selection                 | No request and no upload record                                                                        | Select again                                                                              | Accept one PDF or Markdown file only                                                | Choose one PDF or Markdown file.                                         |

A request error must never clear the current viewer, clear `path_manual`, select a placeholder, or emit a success snackbar. Success must be announced only after the ROM refresh updates the current store. A successful upload followed by refresh failure uses the distinct warning above.

If the user navigates away, the global progress surface may continue to report the single request. Completion must update only the matching ROM identity and must not overwrite a different current ROM. Returning to the ROM fetches authoritative state.

## Accessibility and Universal Input

- Mouse, touch, keyboard, and gamepad must reach the same Upload manual or Replace manual action.
- Keep native DOM order. This is a linear region, so do not add `useGridNav`, custom key handlers, or a parallel focus layer.
- The empty dropzone remains activatable with click, Enter, Space, and gamepad confirm through existing `RDropzone` behavior.
- The explicit footer `RBtn` is the keyboard/gamepad alternative to drag and drop for an existing manual.
- Input labels are state-specific: `Upload manual` when empty and `Replace manual` when a manual exists.
- Download, Re-download, and Delete icon-only controls keep localized accessible names while pending or disabled; disabling a control must not remove its `aria-label` or tooltip text.
- Set `aria-busy="true"` on the manual region while uploading or refreshing. Provide a localized `role="status"`, `aria-live="polite"` status for the pending label. NotificationHost already announces completion and errors.
- Do not move focus on start, progress, success, or error. Focus remains on the initiating control when possible. Native picker cancellation returns to its opener. No overlay scope is added.
- Pending controls must expose disabled semantics and cannot remain activatable underneath the loading state.
- The viewer stays scrollable and readable while pending. Manual delete and re-download controls are disabled, not hidden, so layout and spatial position remain stable.
- Focus rings remain visible only for `data-input="key"` and `data-input="pad"` through existing global tokens.
- Touch and gamepad targets remain at least 44px. The file picker and button require accessible names in all states.
- Do not announce per-progress-event percentage through a live region. Announce the state transition once, then success, warning, or error.

## Responsive Behavior

- Preserve the existing ManualSubtab flex layout and its `70dvh`, minimum 20rem viewer behavior on `sm-and-down`.
- Use `useBreakpoint` and existing `html[data-bp]` selectors only. Do not add layout media queries.
- At xs, the dropzone, helper text, viewer, and full-width action remain within the inherited global `--r-row-pad` gutter with no horizontal scrolling. This phase does not redefine that gutter.
- The existing footer button stays full width at every tier. Do not collapse its Upload/Replace label to an icon because the verb communicates ownership intent.
- UploadProgressToast keeps its existing bounded width and filename truncation. It must not cover the footer action or make the manual viewer unusable at 320px.
- Large viewports gain no additional panels, details, or side-by-side replacement surface.

## Semantic Mutation Inventory Guardrail

This section is a test contract, not a visual contract.

The final active-v2 inventory must extract and classify all of these supported transport forms from every production v2 module and reachable shared API service:

| Form                                                               | Required resolution                                                   |
| ------------------------------------------------------------------ | --------------------------------------------------------------------- |
| `fetch(url, init)` and `window.fetch(url, init)`                   | Resolve URL and static method; absent method is GET                   |
| Callable imported client, such as `api(config)` or `axios(config)` | Resolve static `config.url` and `config.method`; absent method is GET |
| `api.request(config)`                                              | Resolve static `url` and `method`; absent method is GET               |
| Existing `api.get/post/put/patch/delete/head(url, ...)`            | Preserve current method-member and route resolution                   |
| Safe aliases and immutable consts                                  | Follow default, named, namespace, and unambiguous aliases             |
| Literal, template, or reducible concatenated routes                | Normalize through the existing bounded placeholder rules              |

Method, URL, receiver, config, computed key, spread, alias, or wrapper syntax that is rooted in a recognized transport but cannot be reduced statically must fail closed with the existing bounded, path-redacted diagnostic. It must never disappear from inventory or default to CONTROL_PLANE.

Negative fixtures for direct fetch, callable clients, and `request(config)` must enter through `finalInventorySource`, not through manually constructed `RawCall` values. The live `ingestPlaySessionsKeepalive` POST in `frontend/src/services/api/play-session.ts` must appear as a safe database/control-plane authority. Existing route authority classification and the zero-forbidden-live-authority assertion remain unchanged.

No runtime error, toast, setting, progress indicator, or user-facing copy is associated with this guardrail.

## Anti-Patterns

- Multiple primary-manual file selection, `Promise.allSettled`, request fan-out, or last-response-wins state.
- Deleting or truncating the current manual before replacement success.
- Clearing the current viewer or applying optimistic `path_manual`.
- Leaving drop, upload, delete, or re-download active during replacement.
- A fire-and-forget event with no visible pending state.
- A new upload target dialog, source-folder option, confirmation modal, card, drawer, or color token.
- Hard-coded user-visible strings, raw colors, raw Vuetify controls, or direct HTML controls where an R* primitive applies.
- Success copy before the authoritative ROM refresh.
- Warning or error copy that incorrectly says the existing manual is unchanged after the server has succeeded.
- Raw backend errors or storage paths in a snackbar.
- Inventory extraction that silently ignores a recognized transport form.
- Any active-v2 affordance that writes shared/source manuals or external files.

## Verification and Acceptance

### Automated frontend

- A ManualSubtab feature test proves one picker/drop gesture produces one service POST and never a promise fan-out.
- The feature test proves the viewer remains mounted and `path_manual` is not changed optimistically while pending.
- Pending-state tests prove upload/drop/delete/re-download are blocked, `aria-busy` is true, and the button exposes loading.
- Failure tests prove the existing viewer remains, safe copy is announced, and retry becomes available.
- Empty-state failure proves no phantom manual appears.
- Success tests prove refresh precedes success copy and the updated cache-bust/viewer renders.
- Refresh-failure tests prove the distinct reload warning and no false unchanged-manual claim.
- A concurrency test proves a second local gesture cannot start another request and a server conflict maps to the conflict copy.
- Permission tests prove users without `rom.edit` see no upload/replace action.
- Inventory tests cover global/member fetch, callable clients, `request(config)`, immutable configs, unresolved configs, and the live play-session keepalive call through the production extraction path.
- `sourceMutationControls.test.ts` continues to prove that no external mutation control is active.
- Run typecheck, focused Vitest, full frontend tests, build, scoped lint/Trunk, locale parity, locale sorting, and `git diff --check`.

### Manual UI

Verify in both v2 themes and at xs, sm, md, lg, and xl:

- Empty upload, existing replacement, slow upload, failure, retry, concurrency conflict, and refresh failure.
- Mouse, touch, keyboard, and gamepad can open the picker and recover without a focus trap.
- Focus rings appear only for keyboard/gamepad.
- The old viewer remains readable throughout a slow or failed replacement.
- At 320px, no horizontal overflow occurs and global progress/toast surfaces do not hide the action.
- Screen reader announcements occur once for pending and once for completion/error, with no progress-event chatter.
